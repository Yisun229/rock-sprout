# 岩笋 · Rock Sprout v0.3 实施计划

> **版本主题**：敢用 —— 装坏了能救回来
> **依据**：`文档/路线图-v0.1到v1.0.md` 的 v0.3 一节
> **决定来源**：2026-10-28 六问质询（Q1–Q6 全部拍板）
> **前置状态**：v0.2.0 已完成，`lib.rs` 注册 18 个命令
> **工期**：2.5–3.5 周（路线图预留 3–4 周）

## §0 本版决定清单

| # | 事项 | 决定 |
|---|---|---|
| 1 | v0.3 第一优先 | **原子写**。合包写完再替换，失败时旧包还在 |
| 2 | 快照保留策略 | 自动保留最近 **3** 份；另设**手动保存点**，不参与自动清理 |
| 3 | 快照成本 | 一份约 2–5 MB（合包只含改动内容，不是 2.4 GiB 全量） |
| 4 | 回滚范围 | pak **和**记账目录一起回滚，避免"列表与游戏不一致" |
| 5 | 回滚前 | 先给当前状态拍一份快照，回滚错了还能回来 |
| 6 | 游戏更新检测 | 记原 pak 的大小 + 修改时间，变了就提示重建并**禁用撤销** |
| 7 | 游戏运行中 | 装 / 卸 / 撤销前查进程，有就拦住 |
| 8 | 残留检查 | (a) 游戏目录里我们的残留 + (b) 记账与磁盘对账；**不做** pak 内 meta 对账 |
| 9 | 陌生产物 | 启动时提示 + 提供"移到备份目录"按钮，**不做兼容、不拦截** |
| 10 | 死代码 | 删掉 `integrate::uninstall` 与 `uninstall_modio`（会直接删 DLL 且不还原） |
| 11 | DLL 判定 | 从"比大小"改成"比 sha256" |

## §1 起点（2026-10-28 实测，非推测）

| 事实 | 值 / 位置 |
|---|---|
| 原 pak | `FSD-WindowsNoEditor.pak` **2,492,632,528 B（2.4 GiB）**，全程只读 |
| 合并包 | `<游戏>/FSD/Content/Paks/mods_P.pak`，历史产物 **2.3–5.2 MB** |
| 合并包写入方式 | `integrate.rs:321-330` 用 `.truncate(true)` **直接清空目标再写**，无 `.tmp`、无 `rename` |
| 谁来加载合并包 | 我们自己的 DLL：`hook/src/lib.rs:115` 显式打开 `Content/Paks/mods_P.pak` |
| 原 pak 是谁打开的 | `integrate.rs:254-255` `fs::File::open` + `repak::PakBuilder`，只读 |
| 已有备份 | 只有 DLL：`game.rs:29-34` `data/game-backup/<dll名>`，`game.rs:50-66` 备份、`game.rs:181-191` 还原 |
| pak 备份 | **不存在**。全项目 `fs::copy` 仅 4 处：DLL×2、本地导入、记账目录 |
| 诊断现状 | `ipc/settings.rs:179-213` 只打印现状，不做对账 |

**结论**：原 pak 从来没有被改过，所以"备份原 pak"没有意义。**真正的风险在写入方式**——不是"改坏了原文件"，而是"写到一半把合并包写废了"。

## §2 本版要解决的三件事

**一、写坏了要能自动挡住。**
现在的写法是先把游戏目录里那份 `mods_P.pak` 清空，再往里灌。中途只要失败，用户手上就是一个半截包。游戏开不起来，而且没有任何提示。

**二、救不回来是因为根本没有存档。**
用户装了 5 个 mod 发现不对，现在的唯一出路是"全删了重来"。要做到"只退这一步"，就得在每次动 pak 之前留一份状态。

**三、看不见的错最可怕。**
`ipc/mods.rs:258-268` 遇到文件不在，会**静默**把 mod 从合并包里跳过，列表却还显示"已装"。用户以为装了 8 个，游戏里其实只有 6 个。

### M3-1 · 原子写（3–4 天）· **P0**

**做什么**：合包改成"先写临时文件，校验通过再换上去"。

**改哪**：`integrate.rs` 的 `integrate()`（`:242`）与 `:321-330` 的写入点、`:518` 的 `bundle.finish()`。

**三步替换法**（只用标准库 `fs::rename`，不需要额外依赖）：

```
1. 写  mods_P.pak.tmp
2. 用 repak 重读 .tmp，校验条目数与预期一致
3. rename  mods_P.pak → mods_P.pak.prev      （旧包不存在则跳过）
4. rename  mods_P.pak.tmp → mods_P.pak
5. 删掉 mods_P.pak.prev
```

**为什么不用"先删再改名"**：那样中间有一个窗口期，游戏正好在这时启动就会崩。用三步法，任何一步失败都能退回去。

**失败处理**：

| 失败点 | 用户看到的 | 恢复动作 |
|---|---|---|
| 1 或 2 失败 | "合并失败，你的 mod 没变" | 删 `.tmp`，旧包完好 |
| 3 成功、4 失败 | "合并失败，你的 mod 没变" | 把 `.prev` 改回原名 |
| 4 成功后进程崩溃 | 无事发生 | 启动时清理残留 `.prev` / `.tmp` |

**怎么验**：
- 正常合并 → pak 生成、游戏可启动
- 把磁盘写满 / 中途 `Ctrl+C` → 旧包仍在，游戏仍可启动
- 启动清理：手工丢一个 `mods_P.pak.tmp` 进去 → 启动后被删除

**Done**：杀掉进程也不会产生半个包。

**实测记录（己完成）**

- 写入点改了：`integrate()` 现在写 `mods_P.pak.tmp`，`bundle.finish()` 返回「写了多少条」，`verify_pak()` 用 repak 重读一遍临时包比对条目数，一致才 `swap_in()` 换上正式名。
- `swap_in()`：先删多余的 `.prev` → 旧包改名成 `.prev` → 临时包改名成正式名 → 删 `.prev`；第 2 步失败会把 `.prev` 改回去，第 3 步失败会删掉临时包并把旧包改回原名。
- 启动清理 `integrate::clean_stale()`（`lib.rs` 的 `clean_stale_paks()` 在启动时调）：只剩 `.prev` 就把旧包改回原名；正式包和 `.prev` 都在就删 `.prev`；`.tmp` 一律删。
- 出错话术 `game::explain_integrate_error()`：`os error 5`（拒绝访问）→「写不进游戏目录（文件被占着）。先把《深岩银河》关掉再试…」；磁盘空间不足 →「磁盘空间不够…」；其它 →「装进游戏时出错（你的 mod 没变）」。三句都点明「旧包还在」这件事。
- 单测 **58 个全过**（新增 6 个：第一次装没旧包、有旧包换新、只剩 `.prev` 改回原名、正式包与 `.prev` 并存只删 `.prev`、半成品 `.tmp` 被清、坏包校验报错）。
- 回归 **33 个场景全过**，其中 v0.3 新增三条：装完不留 `.tmp`/`.prev`、启动时清掉 `.tmp`/`.prev`、合并失败时旧包不动（用同名目录冒充 `.tmp` 制造「拒绝访问」，实际报出上面那句人话，旧包的字节数和修改时间都没变）。
- 没核的：真的 `Ctrl+C` 杀进程、真把磁盘写满——这两条只能用上面那个「同名目录冒充」来近似，风险表里那份「Access is denied 偶发」也没在真机上撞到过。

### M3-2 · 快照与回滚（4–5 天）

**做什么**：每次动 pak 前，把"当前状态"存一份；支持一键退回。

**快照存什么**（必须成对，否则回滚后列表会骗人）：

```
<data>/snapshots/<时间戳>-<原因>/
├── mods_P.pak          （合并包，2–5 MB）
├── installed/          （记账目录整体副本）
└── meta.json           { 原因, 时间, mod 数量, 原 pak 大小+mtime }
```

**保留策略**（对应决定 #2）：

- 自动快照最多留 **3** 份，超了删最旧的
- 手动保存点**不参与**自动清理，除非用户自己删
- 总量预计 < 30 MB

**回滚动作**：

1. 先给当前状态拍一份 `auto-before-rollback`
2. 用 M3-1 的三步替换法把快照里的 `mods_P.pak` 换回去
3. 记账目录整体替换
4. 校验：回滚后 `list_installed` 的条目数 == 快照 meta 里记的数量

**改哪**：新增 `snapshot.rs`；`game.rs:169-194 clear()`、`game.rs:85-126 apply()` 前后挂钩；`lib.rs` 注册 `list_snapshots` / `create_snapshot` / `rollback` / `delete_snapshot` 四个命令。

**怎么验**：
- 装 3 个 → 装第 4 个 → 回滚 → 剩 3 个，游戏里也是 3 个
- 回滚后又想撤掉回滚 → 用 `auto-before-rollback` 再回来一次

**Done**：能连续回滚两次而不乱。

**实测记录（已完成）**

- 新文件 `app/src-tauri/src/snapshot.rs`：`create(reason, manual)`、`list()`、`delete(id)`、`rollback(id)`；目录就是上面那个结构，`meta.json` 里还多记了「手动还是自动」和原 pak 的大小/时间（M3-3 要用）。
- 触发点不挂在 `game.rs` 里，而是挂在**四个会改东西的命令**上（`ipc/mods.rs` 的 `install_mod`、`download_mod`、`import_local`、`uninstall_mod`），动手前调 `snapshot_before(...)`：拍失败只写一行日志，不挡这次操作。
- 回滚顺序和计划一致：先拍 `回滚前` 一份 → 用 M3-1 的 `.tmp`+`swap_in` 换包 → 记账目录整体换回 → 核对条数（对不上就退回「回滚前」并报错）。所以**连着退两次不会乱**：第一次退完留下的 `回滚前` 就是第二次的落点。
- 一处和计划不同的实现决定：快照 `meta.mods == 0` 时，回滚一律删掉当前合并包，不去看快照里当时有没有残留包。理由是「0 个 mod」这个状态的含义就是「游戏里不该有任何 mod」，而游戏目录里的包有可能来自别处（比如用户之前用别的工具装的）。为此新增的日志：快照里记着有 mod、却没存到合并包时，只退记账并 `warn`。
- 界面：设置页多了「装坏了能退回来」一张卡（`app/src/components/settings/SnapshotCard.tsx`），列出所有快照、能存手动保存点、能点「退回到这里」（先弹确认框）和「删掉」。
- 测出来的数字：`cargo test --lib` **63 passed**（新增 5 个：slug 三种写法、拍快照连记账一起存、自动只留 3 份且手动点不动、删完列不出来、id 带斜杠/`..` 被拒）；`_tools/check-all.mjs` **38 个场景 38 通过**（新增 5 条：导入前自动留现场、手动保存点不被清理、退回「一个都没装」、再退回「回滚前」、退回后合并包与记账对得上）。
- 没核的：真断电那一刻的快照（只验了「拍完快照再装」这条正常路），以及快照占多少磁盘（估算 2–5 MB/份，实际没量）。

### M3-3 · 指纹与更新检测（1–2 天）

**做什么**：记住原 pak 长什么样，被人换了要知道。

**改哪**：新增 `game-state.json`；`game.rs:131-162 status_lines()` 里加一项；前端启动时读一次。

```json
{ "main_pak_size": 2492632528, "main_pak_mtime": 1761... , "captured_at": ... }
```

**行为**：

| 情况 | 表现 |
|---|---|
| 指纹一致 | 正常 |
| 大小或时间变了 | 顶部提示"**游戏已更新**，合并包需重建"；**撤销按钮置灰** |
| 原 pak 找不到 | 提示"游戏没找到"，所有写操作置灰 |

**为什么禁用撤销**：旧快照是拿旧数据合成的，塞进新版游戏等于投毒。宁可让用户重建一次。

**怎么验**：手动改一下原 pak 的修改时间 → 重启 → 提示出现、撤销置灰。

**实测记录（已完成）**

- 新文件 `app/src-tauri/src/game_state.rs`：`GameState { main_pak_size, main_pak_mtime, captured_at }` 存在 `<数据目录>/game-state.json`；`current_fingerprint()` 读现在的大小和时间；`capture()` 在**合并成功之后**写一次（`game.rs` 的 `apply()` 里，紧跟 `integrate` 成功那一行）；`check()` 比对，返回 `GameCheck { has_game, recorded, changed, summary, recorded_size, current_size }`。
- 容差：修改时间差 **2 秒以内不算变**（`MTIME_TOLERANCE_MS = 2_000`）。理由见 §6 风险：不同文件系统记修改时间的精度不一样，差一两秒不代表内容变了。
- 三种情况的话术：没找到游戏 →「没找到《深岩银河》（目前只支持 Steam 版）」；没记过指纹 →「还没装过 mod，所以没有可对比的记录」；变了 →「游戏本体好像更新过（主 pak A → B 字节），现在的合并包是上一版游戏的数据，得重装一次 mod」。
- 界面：`App.tsx` 启动时问一次 `game_status`，变了就在内容区顶部挂一条黄条（复用离线那套 `.banner.warn` 样式）；设置页的现场备份卡也自己问一次，变了就把「退回到这里」按灰并写出原因（`snap.rollbackBlocked`：「游戏更新过，旧备份不能用了——先重装一次 mod 再说」）。
- 诊断信息里多一行「游戏本体：…」，用的就是 `check().summary`。
- 数字：`cargo test --lib` **68 passed**（新增 5 个：没记过、一致、2 秒容差、大小变了、找不到游戏）；`_tools/check-all.mjs` **43 个场景 43 通过**（新增 5 条，其中「假装游戏更新」是把主包 mtime 往后拨 5 秒，验完再改回去——最后一条场景正是验「改回去就不提示了」，证明判断真的按指纹走，不是一次性开关）。
- 没核的：Steam 真推一次更新（要等游戏出新版本，没法造）；只读文件系统上写 `game-state.json` 失败时会怎样（代码里只 `warn`，不影响装 mod）。

### M3-4 · 进程检查（0.5 天）

**做什么**：装、卸、撤销之前，先看游戏在不在跑。

**改哪**：`ipc/mods.rs` 的 `install_mod` / `uninstall_mod` / 新的 `rollback` 入口。

**实现**：查进程名 `FSD-Win64-Shipping.exe`。可以用 `tasklist`，也可以引 `sysinfo` crate——**建议直接跑 `tasklist`**，省一个依赖，0.5 天能做完。

**行为**：在跑就返回一句人话——"**《深岩银河》正在运行，请先关掉游戏再操作**"，前端直接显示这句，不要显示 `os error 32`。

**怎么验**：开着游戏点卸载 → 出现提示；关掉 → 正常执行。

**实测记录（已完成）**

- 新文件 `app/src-tauri/src/proc.rs`：跑系统的 `tasklist /FI "IMAGENAME eq FSD-Win64-Shipping.exe" /NH`，输出里「有一行以进程名开头」就算在跑（中文系统的「信息: 没有运行的任务匹配指定标准。」和英文系统的 `INFO: No tasks are running…` 都不会误判）。`output_has_process()` 单独拆出来，好写单测。
- 一个原则：**查不出来就当没在跑**（`tasklist` 起不来、权限不够都只 `warn`）。理由见 §6 风险——宁可让替换动作去撞文件锁，也不要因为查不到就把人拦在门外。
- 拦在五个地方：`ipc/mods.rs` 的 `download_mod` / `install_mod` / `import_local` / `uninstall_mod`，以及 `ipc/snapshots.rs` 的 `rollback_snapshot`；都排在「拍快照」之前（没动手就不该留现场）。错误码统一 `game_running`，前端 `ErrorHint` 里有专属说法：「游戏还开着呢 / 先退出《深岩银河》再试一次——游戏开着的时候它攥着 mod 文件，改不动。」
- 数字：`cargo test --lib` **73 passed**（新增 5 个：中文「没找到」、英文「没找到」、有进程行、名字大小写不同、别的进程）；`_tools/check-all.mjs` **48 个场景 48 通过**（新增 5 条）。
- 怎么造的「游戏在跑」：把 `powershell.exe` 复制一份改名成 `FSD-Win64-Shipping.exe`，用 `Start-Sleep` 撑 12 秒。进程名就是文件名，`tasklist` 看到的名字和真游戏一样，**不用真开游戏**（Steam 那份 8 G，还会把人踢下线）。验完 `taskkill /F /IM FSD-Win64-Shipping.exe` 并删掉那份 1 MB 的假程序。
- 场景顺序也是完整闭环：没跑游戏时照常装 → 假游戏起来后装/卸/回滚/下载四处都被拦（`code === "game_running"`、话里含「正在运行」）→ 假游戏关掉后又能正常装。
- 没核的：真的开着《深岩银河》点卸载（要占着游戏，留给人验）。

### M3-5 · 残留检查与对账（3–4 天）

**做什么**：一个"体检"入口，把"该在的不在、不该在的还在"一次性列清楚。

**新命令**：`audit_game()`，返回结构化报告。

**检查项（决定 #8，只做 a + b）**：

| 类 | 检查内容 | 处理 |
|---|---|---|
| a1 | `mods_P.pak` / `.tmp` / `.prev` 残留 | 提供清理 |
| a2 | `x3daudio1_7.dll` 三态：不存在 / 是我们的 / 是原版 | 只报 |
| a3 | `game-backup/` 里的 DLL 备份是否还在 | 只报（决定卸载能不能还原） |
| b1 | 记账有、磁盘没文件 | 标 `missing`，提供"只删记录" |
| b2 | 磁盘有下载文件、记账里没有 | 提供"清理孤儿文件" |

**复用什么**：`rec.missing` 字段已经存在（`migrate.rs:92-97`）；`maintenance.rs:11-31 delete_record_only` 已经在，只要把入口从"启动迁移"扩展到"用户主动体检"。

**改哪**：新增 `audit.rs`；`ipc/settings.rs` 旁边加命令；前端在设置页加一块"体检"。

**怎么验**：
- 手工删掉一个已装 mod 的文件 → 体检列出"记录在、文件没了"
- 手工丢一个 `mods_P.pak.tmp` → 体检列出"残留"

**Done**：体检报告里每一条都能点一下处理掉。

**实测记录（已完成）**

| 项 | 内容 |

**怎么验**：游戏目录里现在正躺着一个 `FSD-WindowsNoEditor_Mods.pak`（150 MiB，MintCat 遗留）→ 启动后应被识别并提示。

**实测记录（已完成）**

- **陌生产物**：体检多一类 `stray`——扫 `FSD\Content\Paks` 里既不是游戏主包、也不是 `mods_P.pak` 的 `*.pak`，报「游戏目录里有 N 个不认识的文件」，处理动作 `move_stray` 把它们挪进 `<数据目录>\game-backup\stray\stray-<时间戳>\`，**不删**。这台机器上 MintCat 留下的 `FSD-WindowsNoEditor_Mods.pak`（156,325,146 字节）被点名了——但**没动它**：那是用户自己的东西，体检只负责说出来。
- **死代码**：`integrate.rs` 里 `uninstall()` 与 `uninstall_modio()` 共 113 行已删（前一个会直接删 DLL 且不还原，是隐患）。删完顺带清掉三个变成没用的 import（`ErrorKind`、`serde::Deserialize`、`snafu::Whatever`）和 `hook_dll_len()`。原文件留了份快照在 `_tools\_integrate-backup.rs`，确认没问题后可以删。
- **DLL 判定改 sha256**：`integrate::hook_dll_sha256()` 把内嵌的加载器算一次哈希记住（`OnceLock`），`game::is_our_dll()` 改成算游戏目录那个文件的 sha256 再比。理由写进代码注释：换个编译选项大小就变，靠大小会认错。
- 数字：`cargo test --lib` **79 passed**（新增/改写 2 个：陌生产物的挑选规则、空数据目录不该有能修的问题）；`_tools/check-all.mjs` **56 个场景 56 通过**（新增 3 条，其中「别家工具那个 150 MB 的包也被认出来」只在文件真存在时才跑，且断言它**没被挪走**）。
- 没核的：在陌生产物真被挪走之后再装一次 mod 能不能正常工作（按设计那样做会少一个别的工具写的包，但游戏目录里到底谁赢取决于加载顺序，不测更清楚）。

## §4 不做清单

| 不做 | 理由 |
|---|---|
| 备份原 pak（2.4 GiB） | 它从来没被写过，备份一份永远不会去读的文件没有意义 |
| pak 内 meta 与记账对账 | 价值低、实现绕，v0.3 先不做 |
| 自动删陌生 pak | 别人的文件，只能提醒和移走，不能替他决定删 |
| 存档相关的一切（等级 / 解锁 / 时装） | 那是 v1.1 之后的伴侣功能 |
| 换 UI 视觉 | 按 v0.2 的决定，视觉留到 v0.5 |
| 压缩快照 | 2–5 MB 的东西，压缩省不了多少还多一层出错可能 |

## §5 验收（能演示的六件事）

1. 合并过程中强杀进程 → 游戏仍能正常启动，旧 mod 还在
2. 装 5 个 → 再装 1 个 → 一键回滚 → 回到 5 个，列表与游戏一致
3. 回滚错了 → 用"回滚前的快照"再回一次
4. 手动改原 pak 时间戳 → 启动提示"游戏已更新"，撤销按钮变灰
5. 开着游戏点卸载 → 提示"请先关掉游戏"
6. 删掉一个已装 mod 的文件 → 体检列出它，点一下"只删记录"就清干净

**核到哪了**

| # | 验收 | 情况 |
|---|---|---|
| 1 | 合并中强杀进程 → 游戏还能启动、旧 mod 还在 | **部分核**：合并失败（把 `.tmp` 位置占住制造「拒绝访问」）时旧包大小与时间都没变，启动时也会自动清残留；真强杀进程没试（时序太难捏，风险低——写的是 `.tmp`，正式包在换名前一刻都没动过） |
| 2 | 装 5 个 → 再装 1 个 → 回滚 → 回到 5 个 | **已核**：用「导入两份 → 回滚」的等价场景验过（列表与合并包一起退） |
| 3 | 回滚错了 → 用「回滚前」的快照再退一次 | **已核**：连着退两次的场景在回归里 |
| 4 | 手动改原 pak 时间戳 → 提示「游戏已更新」、撤销变灰 | **已核**：把主 pak 时间往后拨 5 秒，提示出现、按钮变灰、改回去就恢复正常 |
| 5 | 开着游戏点卸载 → 提示「请先关掉游戏」 | **已核**（用改名成 `FSD-Win64-Shipping.exe` 的 powershell 冒充游戏进程）；真开着游戏没试 |
| 6 | 删掉一个已装 mod 的文件 → 体检列出、点一下清干净 | **已核** |

## §6 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 三步替换在 Windows 上偶发 `Access is denied` | 合并失败 | 具体错误码映射成人话；提示关杀软/关游戏 |
| 快照与记账回滚不同步 | 列表骗人 | 回滚第 4 步强制校验条目数，不一致就报错并回退到"回滚前快照" |
| 用户手动删了 `snapshots/` | 撤销不可用 | 快照列表读不到就直接隐藏撤销入口，不报错 |
| 原 pak 指纹判断误报（mtime 精度） | 每次启动都提示更新 | 只在**大小**变化或 mtime 差异 > 2 秒时才判定为变 |
| `tasklist` 在某些精简系统上不可用 | 检测失效 | 检测不到就当"没在跑"，不阻断操作 |
