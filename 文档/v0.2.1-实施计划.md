## §3 里程碑拆解

### M0 · 修 Guid 读取 bug（P0，先于一切）

**现象**：Rust 输出的 `SavegameID`、`KPIGuid`、`PerkID`、`WeaponID`、配装里的武器 GUID **全部是 0**；同一份存档用 JS 解析出来的却是真值。

**根因**（已定位）：
- `app/src-tauri/src/save/model.rs:311-316` `as_guid` 只匹配 `Value::Binary`
- 但 `app/src-tauri/src/save/gvas.rs:555-568` 对裸结构体返回的是 `Value::Struct { props: [Property { name: "$binary", value: Value::Binary(..) }] }`

**修法**：`as_guid` 增加对 `Value::Struct` + 单字段 `$binary` 的识别（或在 `structured()` 处直接把 16 字节判成 Guid）。**二选一，改一处，不要两处都改**。

**验收**：
1. 主档 `SavegameID` 解析出非 0，且与 JS 参考实现（`_tools/_gvas.mjs`）逐字节一致
2. 54 条 `KPIGuid` 不再全 0（`_tools/_m2-first.json` 里 54 条 unique=1 即此 bug 的物证）
3. 补单测：裸 Guid 结构体、数组元素内的 Guid、map 键的 Guid 三种位置各一条

> 这个 bug 不影响 v0.2.0 用户看到的画面（那版只显示数字和资源名），但**v0.2.1 之后每一步都建立在 GUID 上**，所以必须第一个修。

### M1 · 结构表（单独提交、单独验收）

| 表 | 状态 | 内容 | 验收 |
|---|---|---|---|
| `levels.json` | **数据已确定** | 25 级累计阈值（0/3000/7000/…/315000），四职业共用，315000 = 25 级封顶 | 反算正确：**7047 → 3 级、8121 → 3 级**（两者都在 7000–12000 区间）、**315000 → 25 级**；**边界用 `bisect_right` 语义**，XP 恰等阈值算高一级（3000 → 2 级，不是 1 级） |
| `milestone-names.json` | **卡在缺 GUID** | 当前版本 67 条（名称/目标/分级/每级点数），但 **GUID→名称没有任何公开来源** | 见 §5「里程碑 GUID」；没有映射前不显示名字 |
| `milestone-tiers.json` | **已判定** | `Tier` = 该里程碑**已领到第几级**（1-based，上限 = 该条的分级数） | 依据：反射结构 `FMilestoneCounter` 只有 `KPIGuid + Tier` 两个字段，`UMilestoneAsset` 有 `Tiers[] / GetClaimedTier() / ClaimNextTier()`；7 份真实存档 Tier 恒 ≤ 5、且值域含 1 和 4（排除「点数」解释） |

**每级天赋点**：职业等级里程碑 5 点（各 1 级）；`Complete Missions` / `Complete Secondary Objectives` 3 点/级；其余全部 2 点/级。按当前 67 条逐级累加 = 640 点（旧 56 条版本约 529 点，与 wiki 正文吻合；wiki 另一处写 893 点，与表格对不上，**不采用 893**）。

**已核对（M0 后实测，原先的怀疑不成立）**：主档 **54 条记录 / 54 个不同 GUID**，Tier 分布 `{1:9,2:11,3:11,4:17,5:6}` 合计 54，**没有 `Tier=0`**。计划里那个「56」是 33 份存档合起来去重后的数量，不是主档吞了记录。这条已结案。

> 每张表都要写 `$source` / `$verify`，格式照 `names.json`。

### M1b · 一次性导出四类名字表（走 UE4SS，用户只进一次游戏）

**目标**：产出四张表，键都是 32 位小写 GUID：

| 表 | 值 | 供哪版用 |
|---|---|---|
| `milestone-names.json` | `{ en, tiers, pointsPerTier }` | v0.2.1 |
| `weapon-names.json` | `{ en, class }` | v0.2.2 |
| `equipment-names.json` | `{ en, class, slot }` | v0.2.3 |
| `skin-names.json` | `{ en, class, type }` | v0.2.4 |

**为什么一次导四类**：这四类资产都在内存里，同一个探针、同一次进游戏就能全拿到。分开导等于让用户开四次游戏。

**做法**：只读 Lua 探针，绑热键（默认 F10）。**每次按下做一轮抓取并 append 到日志，多轮结果合并不覆盖**——不同资产要打开不同界面才会加载进内存。

**用户操作（一次会话内做完）**：进空间站 → 打开 KPI 终端按 F10 → 去武器工作台按 F10 → 去衣柜/外观按 F10 → 退出。

**兜底要求**：抓不到某类时，探针必须同时输出**已加载对象的类名分布统计**（类名 + 数量），下一次照着类名改，不用瞎猜。

**规矩**：

1. **只读**，不写存档、不改游戏目录里的既有文件；探针放在 Mods 下一个独立文件夹，导完即删
2. 游戏目录现在只有一套在生效（MintCat 装的 `dwmapi.dll` + `ue4ss\UE4SSL.dll`，`ue4ss\UE4SS.log` 仍在写）；我们的 `x3daudio1_7.dll` 已是原版大小、没在跑。**不要动那一套**，只在它的 `mods\` 下加自己的文件夹
3. 导不出 `FormattedTitle` 时退而读 `FormattedDescription` 或资产名，**并在报告里说清读的是哪个字段**
4. 导完把原始日志原样贴回来，不要手抄

**验收**：

1. 里程碑：拿主档那 **54 个 GUID** 去核对，命中率必须 **54/54**
2. 武器 / 装备 / 皮肤：各自与 `Loadouts` / `ItemUpgradeLoadouts` / `UnlockedVanityItemIDs` 里出现的 GUID 集合比对，**出现在存档里却导不出来的一律列出来**，不许静默略过
3. 里程碑抽 5 条让用户在游戏里看 KPI 终端对名字，全对才算过
