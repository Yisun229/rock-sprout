## §1 验收（这一版算做完的标准）

跑 `node _tools/check-all.mjs` 全绿，且下面五条各自有证据：

1. 「装备」页能列出角色槽，每个有进度的槽展开成三套配装，每套**固定八格**（主武器 / 副武器 / 移动工具 / 职业工具 / 护甲 / 照明弹 / 镐 / 手雷），空的写「没装」，位置不跳
2. 点任意一件装备开抽屉，能看到名称、所属武器、以及（若 M4 成功）改装清单与已解锁状态
3. **职业识别二选一必须成立**：要么全认出来、页面按职业分块；要么认不全、页面按角色分块且认不出的写「认不出职业」。截图为证，不许两种混着用
4. 五张卡不再显示旧数据（改存档后切回「我的数据」，数字跟着变）
5. `cargo test --lib --offline` 全绿；新增字段解析至少有 6 条单测（八槽位读数、空槽、未知 GUID、已解锁并集、职业反推命中、反推落空）

## §2 现状（写计划时实测）

**后端 `app/src-tauri/src/save/`**：`gvas.rs`（读取器）、`locate.rs`（找存档）、`model.rs`（字段）、`store.rs`（缓存）、`tests.rs`

**已注册的 4 个存档命令**（`lib.rs:97-100`）：`save_overview` / `save_list` / `set_save_file` / `save_debug`

**前端**：`app/src/pages/MyData.tsx`（368 行，四块：概览 / 矿物 / 角色 / 里程碑）

**已有数据表 `app/src/data/`**：
- `names.json`：`classes`（4 条，键是 `/Game/Character/DrillerID.DrillerID` 这类路径）、`resources`（14 条 GUID→名字）、`overclocks`（**149 条 GUID → `{en, weapon, class}`**，`class` 是 `scout`/`driller`/`gunner`/`engineer` 小写）
- `milestone-names.json`：56 条，带 `tiers:[{count, perkPoints}]`
- `levels.json`：25 级累计阈值
- `NOTICE.md`：数据来源与许可

**存档里能读到的东西**：
- `CharacterSaves[i].Loadouts[3]`：每套配装 8 个槽位 GUID（顺序与游戏一致）
- `ItemUpgradeLoadouts`：一张 武器 GUID → 已装改装 GUID 的表（**键是武器 GUID**）
- `PurchasedItemUpgrades`（124 个）/ `PermanentUpgrades`：全档一份，**不分武器**
- `CharacterSaves[i].CharacterClass = None`、`SavegameID` 全 0 —— **职业读不出来**

**关键缺口**：`ItemUpgradeLoadouts` 的键是武器 GUID，但我们手上没有「武器 GUID → 武器名/职业」的表。`names.json` 的 `overclocks` 给的是**超频 GUID → 武器与职业**，不是武器 GUID。

## §3 里程碑

### M0 · 已完成（2026-11-05），结论如下，不再重做

**M0a 五张卡的陈旧数据 —— 已在 v0.2.1 修完。**
根因是「页面切走不卸载，卡片只在挂载时读一次」，已改成按当前页重读，共 6 处（`7baa4f2` 备份卡 + `981171a` 体检 / 令牌 / 数据目录 / UE4SS / 我的数据），回归 108/108。

**M0b「武器 GUID → 职业」找到了，走的是第 3 条路（v0.2.1 已抽好的资产表），不依赖 M4。**

| 试过的路 | 结论 |
|---|---|
| ① 从 `Overclocking` 反推 | **不成立**：`names.json` 那 149 条是**图纸 ID**（`SchematicSave` 60 条命中 36），而存档里 `EquippedOverclock` 存的是**改装项自己的 GUID**，两套 ID 空间不重叠（`ItemUpgradeLoadouts` 158 条命中 0） |
| ② 配装 × 改装表交叉 | **走到头**：两边都只有 GUID，没有名字也没有职业 |
| ③ 游戏自己的 ID 资产 | **命中**：`_tools/assettable.json` 的 57 条武器里，52 条带职业；33 条带 `wpnRef` 的都是武器/工具主体且全部带职业 |

**职业识别已实测可成立**：主档 4 个有进度角色全部落到具体职业（例：角色 1 → Driller、角色 2 → Engineer、角色 3 → Gunner）。

**一处必须澄清，别按错的理解做**：`assettable` 里 5 条没有职业的是 `BP_Bosco`（无人机）、`WPN_ResonanceScanner_Builder`、以及 3 条 `WPN_Pickaxe_*`（三条共用一个 `wpnRef`，所以拿不到职业）。**这五个都不在判据范围内**——判据只看角色的**主武器与副武器**，镐和扫描仪不参与。所以**没有「有一个认不出就整页按角色」的必然性**，本版应当走**按职业形态（Q1=c 理想形态）**。

**产出**：`_tools/v0.2.2-字段结论.md`（已写）。

### M1 · 武器与工具名称表（1 天）

- 新建 `app/src/data/weapon-names.json`：`{ "<武器 GUID>": { "zh": "…", "en": "…", "class": "scout", "slot": "primary" } }`
- **以 `_tools/assettable.json` 的 57 条打底**（已有 `gid` / `idAsset` / `class` / `wpnRef`），人工只补中文名与槽位归类，**不再手抄 GUID**
- 覆盖八个槽位：主武器 / 副武器 / 移动工具 / 职业工具 / 护甲 / 照明弹 / 镐 / 手雷。33 条带 `wpnRef` 的条目就是武器与工具主体
- 镐的三条 `WPN_Pickaxe_*` 职业为 `null`，可**按资产名后缀**（`_Driller` / `_Engineer` / `_Gunner`）推断；推断失败的显示「镐」，不带职业——它不影响识别
- 数据源写进 `NOTICE.md`（沿用现有格式，注明来源与许可）
- 机器不可读的名字不许编：查不到就留 `null`，页面显示 `#GUID 前 8 位`

### M2 · 职业识别（0.5 天）

- 新增 `CharacterInfo { slot: usize, class: Option<Class>, basis: Option<String> }`
- **判据（Q2=a）**：取该角色 `Loadouts[0..3]` 里的**主武器 GUID 与副武器 GUID**（只看这两个槽，不看镐、扫描仪、护甲）→ 查 `weapon-names.json` 的 `class` → 命中即定；多个槽位命中且冲突时，**不算认出**（不投票、不取多数）
- **按实测预期应走「按职业」形态**：4 个有进度角色已全部认出（见 M0 结论）。若实现后仍出现认不出的，才退回按角色
- 全部 5 个槽都认出 → 页面按职业组织（**Q1=c 理想形态**）
- 有任意一个认不出 → 整页按角色组织，认不出的那块标题写「认不出职业」（**Q3=a**）
- 空槽（没进度的）不参与判定，也不算「认不出」

### M3 · 装备页（1.5 天）

- 新页 `装备`，放在导航「矿层」组里、`我的数据` 之后
- 每块：标题（职业名或「角色 N」）+ 三套配装；每套一行八格，固定顺序，空槽灰字「没装」
- 点任意一格开右侧抽屉，复用 `ModPreview` 的交互（Esc / × / 点空白关）
- 抽屉内容：装备名、所属武器、所属职业、槽位；M4 成功时追加改装清单
- 不标「当前穿的是这套」（决策 2）

### M4 · 改装树抽取（2 天，可降级）

- `app/src-tauri/src/devtools/assetdump.rs` 增加一种 dump：从 pak 读改装资产，导出 `app/src/data/upgrades.json`
- 每条：`{ id, en, zh?, weapon, tier, requires }`（`requires` = 前置改装）
- 名称走 locres；**限半天**，解不出就显 `#id`（决策 11）
- 失败即降级，**不砍整版**（决策 8）

### M5 · 已解锁判定（0.5 天）

- `已解锁 = PurchasedItemUpgrades ∪ PermanentUpgrades`（决策 6）
- 页面在改装清单上显示「已解锁 / 未解锁」，并在脚注写明：**全档一份、不分武器**，所以这里只回答「这一项解锁没有」，不回答「这把枪解锁了几个」
- 不做「总加成」汇总（决策 7）

### M6 · 回归与发布（1 天）

- 回归场景至少补 5 条：装备页八格固定、空槽显示「没装」、抽屉开关、职业识别两形态各一条（用两份不同的存档夹具）
- 版本号 0.2.2（三处）；出安装包 + 便携包；`SHA256SUMS.txt` 只留这一版两行
- 发布说明里必须写清：**改装树是本版新抽的、职业名靠武器反推（不是存档里读的）**

**合计约 7 天**（M0 1 + M1 1 + M2 0.5 + M3 1.5 + M4 2 + M5 0.5 + M6 1）。M4 失败则为 **5 天**。

## §4 明确不做

1. 不写存档、不改存档（本版全程只读）
2. 不做「当前穿的是这套」的标记
3. 不做总加成 / DPS 计算 / 推荐搭配
4. 不做超频（overclock）的装备与解除——`names.json` 里虽有 149 条超频名字，本版**只用于反推职业**，不展示
5. 不按武器统计已解锁数量（数据不支持，见 M5）
6. 不改现有 25+ 个命令的签名
7. 不重做布局与配色

## §5 风险与砍点

| 风险 | 概率 | 处置 |
|---|---|---|
| 五张卡 bug 根因复杂，修不动 | 中 | 超过 1 天就先隔离（明确写「切页后需手动刷新」），继续往下做，别卡住整版 |
| 武器 GUID 一条路都拿不到 | 中 | 退到 M4 抽取；M4 也失败 → 职业识别整体不显示职业，页面固定按角色（Q1/c 的兜底形态） |
| 改装树结构与预期不同 | 中 | 立刻降级到「只显示已装」，M4 记入附注 |
| locres 解不出中文名 | 中 | 显英文原名 + `#id`，不编 |
| 存档里 8 个槽位顺序与游戏不一致 | 低 | 用两份不同存档交叉验证；不一致时以「有值的那几个槽优先，空槽排后」为临时规则并**在页面注明** |

**砍点顺序（先砍后面的）**：M5 脚注说明 → M4 整条 → M0b 的第 3、4 条路 → M3 抽屉详情简化。**M2 与 M3 不许砍**，它们就是这一版的全部。

## §6 边界

- 只读。任何会写存档、改游戏目录行为的操作都不在本版
- 新增命令可以，现有命令签名一个都不改
- 数据表只放 `app/src/data/`，解包原始资产放 `_tools/`（已被 `.gitignore:2` 忽略）
- 提交用显式路径，不用 `git add -A`
- 每完成一个里程碑给一份「实际做了什么」，含实测数字与踩到的坑
