# v0.2.3 M1：命名与契约

写给后面改这块代码的人。三条都不是「风格问题」，是按错的方式写就会静默出错的地方。

## 1. 武器表和超频表用的是两套命名

- `app/src/data/weapon-names.json`：键是武器 GUID（32 位小写十六进制），值里有 `zh` / `en` / `class` / `slot` / `folder`。`en` 是从资产名去掉 `WPN_` / `ID_` / `BP_` 前缀得来的显示名。
- `app/src/data/overclocks.json`：每条超频的 `weapon` 字段是**武器资产所在的文件夹名**（例如 `BoltActionRifle`、`FlameThrower`）。

两套名字**不保证相等**（M1000 的资产文件夹是 `BoltActionRifle`，显示名却是 `M1000`）。M1 最初算「这把武器有几条超频」时用显示名去对，于是 M1000、转管机枪一律显示「共 0 条」——不是数据缺失，是 key 取错了字段。

**正确做法**：用 `weapon-names.json` 的 `folder` 去对 `overclocks.json` 的 `weapon`。不要用 `en`，也不要用中文名。

## 2. `oc_total` 按武器资产计数，与角色槽位无关

同一把武器会出现在多个角色、多套配装、多个格子里（主武器格、职业工具格都可能出现同一个 GUID）。`oc_total` 的语义是「这把武器一共有几条超频」，**只跟武器资产有关**，跟它在哪个角色的哪套配装无关。

所以：
- key 用武器资产（`folder`），查表结果整页共用；
- 如果哪天发现「同一把枪在不同格子里 `oc_total` 不一样」，那就是 key 又退回到按槽位算了，是 bug，不是数据问题。

## 3. 空格子的契约（前后端约定）

- 后端：格子里没装东西时，返回 `oc_total = 0`、`oc_open = false`、`overclock = null`。
- 前端：`oc_total > 0` 才渲染整段超频（包括「已开放 / 还没开放」那行）。

空格子看不到超频段是刻意的：没有武器就没有超频，给个 0 反而像数据出错。改一边就要同步改另一边。

## 4. 旧脚本已废弃

`_tools/_slots.mjs`、`_tools/_slots3.mjs`、`_tools/_probe2json.mjs` 这三个一次性脚本会**整体重写** `weapon-names.json`，跑一次就把 `folder` 列静默抹掉且不报错。它们已归档到 `_tools/_attic/`（文件名加 `attic-` 前缀、开头有废弃说明）。

要改名称表，一律用 `_tools/_weaponNames.mjs`。它自带两条护栏：重生成时逐条比对旧表的 `zh` / `en` / `class` / `slot` 四列，不一致就停下不写盘；连跑两次输出逐字节一致（`--out` 生成两个临时文件后比 sha256 可验）。

## 5. 皮肤 / 喷漆 / 十字镐的名字：这一版没有

读完 pak 里的资产后确认：这三类和超频不是一套机制。

- 超频：资产里直接存 FText 名字键（177 个 `nameKey` 全是 `OC_*`），键能在 locres 里查到。
- 皮肤：594 个 `SKN_*` 资产里**只有 98 个**带名字属性（`SkinName`）；这 98 个指向 **10 张不同的字符串表**、76 个不同的键，另有 62 条是内嵌英文原文（表 id 为空）。剩下 **496 个**资产根本没有名字属性，只有 `SkinSet` / `SkinEffect` / `OwningCharacter` / `SaveGameID`——它们的名字挂在 `SkinSet` 指向的另一个资产上，那个资产不在这批抽取里。

所以这一版按「名字配不出来」处理：页面上相关块整块收起来、写一句「名字暂时显示不出来」，只保留数量这类已知信息；**不用 `#编号` 填充页面**（那不是降级，是把没做完的东西摆出来）。

654（这批抽到的皮肤资产数）和 280（存档里这位玩家解锁的皮肤数）不是一个口径，差的 374 条既包含没解锁的，也包含上面那 496 个没有名字属性的。下一版先用 `SkinSet` 这一层把名字接上，再谈覆盖率。
## 6. 皮肤名字：按命名空间查表，四档统计

查表不能「键全局扁平查」——不同字符串表里有同名键，扁平查会拿到别人的名字。实测过一次：`SKN_Scout_DLC10_Knight` 拿到 `Biohazard / 生物危害`，查不到报错，看起来完全正常。

现在改成按命名空间查：`SkinName` 的 `table_id` 末段先拿完整串撞命名空间，撞不到再从尾部逐段剥（**最长优先**，不允许从头短匹配）。候选命名空间多于一个、或键在多个命名空间里都存在，都算歧义，记进清单而不自行挑选。

594 条皮肤的四档：

| 档 | 条数 | 含义 |
|---|---|---|
| 1 可信 | 348 | 命名空间唯一且键命中，中英都来自同一张表 |
| 2 歧义 | 0 | 本次没有出现候选或键的歧义 |
| 3 只有英文 | 246 | 表里没有，退回资产自带的英文原文 |
| 4 都没有 | 0 | — |

一条需要人来判断的记录：`SKN_Scout_DLC10_Knight` 在第 1 档里，命中的命名空间是 `Strings_DLC07`——也就是说**资产自己的 `table_id` 就指向 Biohazard 那张表**，不是查错。这属于游戏数据本身的问题，先按数据如实显示，后续若确认是游戏 bug 再单独处理。
## 7. 两轮数字怎么对上（对账口径）

先报过「246 条只有英文」，后报「188 条 asset + 118 条 derived」，看着冲突，实际是同一批：

- 246 = 188 条真有资产自带英文 + 58 条英文也为空（改用去前缀兜底）
- 654 = 594 个皮肤资产 + 60 条没有对应资产的 `SKS_*` 旧条目
- 118 derived = 上面的 58（有资产、但表里没有且资产也没英文）+ 60（根本没有对应资产）

**对账结论**：`348 + 188 + 58 + 60 = 654`，与四档的 `348 / 246 / 0 / 0`（共 594 个资产）+ 60 条旧条目完全一致。以后看到这两个数不要当矛盾，口径分别是「按资产」和「按表内条目」。

十字镐同理：160 条 = 151 table + 4 asset + 5 derived（这 5 条是没有对应资产的旧条目）。
