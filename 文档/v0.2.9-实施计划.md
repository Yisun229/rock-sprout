# v0.2.9 实施计划 · 启用 / 停用 mod

> **依据**：`文档/路线图-v0.1到v1.0.md` §4「v0.2.9 启用 / 停用 mod：文件保留、不参与合并、界面标「已停用」」
> **一句话目标**：能把一个已经装好的 mod 暂时关掉——文件还在、记录还在、随时能开回来，但它不再进合并包。
> **定位**：这是第一个会**改既有行为**的版本（合并包可能被删、冲突报告的顺序会变），不是纯加功能。

## §0 决策（十四项，全部已拍板）

| # | 决策 | 为什么 |
|---|---|---|
| 1 | 背包页**每行一个开关**，批量栏再加「停用所选 / 启用所选」 | 停用是高频小动作，每次都要勾选再点按钮会烦 |
| 2 | 停用**仍算已装**，标题写「已装 12（其中 2 个停用）」 | 拆成两堆会让用户在两个区域来回找 |
| 3 | **脚本 mod 也支持停用** | 用户明确要求；本机有 2 个可当夹具 |
| 4 | 全部停用时**删掉 `mods_P.pak`** | 留空包会让游戏加载没用的东西，还多一个假线索 |
| 5 | 停用的 mod **照常检查更新**，更新后保持停用 | 停用常是「暂时不想要」，不是「再也不想要」 |
| 6 | 脚本 mod 停用 = **删 `enabled.txt`**（启用 = 写回空文件） | 最小可逆操作；不挪目录，不存在挪错丢文件 |
| 7 | 切换**不生成快照** | 快照防的是「删了就没了」，而停用一个字节都不删；快照不做内容比对，每次会白复制 5 MB |
| 8 | 点开关**立即重建**合并包 | 实测 484–535ms，延迟反而制造「我到底停掉没有」的疑问 |
| 9 | 脚本类行内提示**「重启游戏后生效」** | 防「我停用了它还在跑」变成 bug 报告 |
| 10 | 冲突检测与预检**排除已停用的** | 不进合并包就不该出现在「谁覆盖谁」里 |
| 11 | **顺手修**合并序与冲突序不一致 | 合并按名字字母序、冲突检测按安装时间序，现在报的可能不是实际结果 |
| 12 | 「今天」页更新块**混合计数**：「有 12 个新版本（其中 3 个已停用）」 | 与决策 2 同口径：停用不是「不在列表里」 |
| 13 | 批量栏**不加「全部停用 / 全部启用」** | 一击清场且会删包，不该放在高频操作区；全选 + 批量已能达成 |
| 14 | 停用的条目**留在原位**，靠灰显 + 徽章区分 | 沉底会让「我刚停的那个去哪了」变成新问题 |

## §1 数据契约

### 1.1 记账加一个字段

`app/src-tauri/src/ipc/mods.rs:57-84` 的 `InstalledRecord` 加：

```rust
#[serde(default)]
pub disabled: bool,
```

- `#[serde(default)]` 是**必须的**：老的 12 字段 JSON 要能直接读成 `disabled: false`，不写迁移脚本
- 前端 DTO（`InstalledMod`，`mods.rs:26-41` / `api.ts:151-165`）同步加 `disabled: boolean`
- 快照里的 `installed/` 是整个目录的复制，新字段自动跟着快照与回滚，**不需要额外处理**

### 1.2 脚本 mod 的开关

`app/src-tauri/src/ue4ss_mods.rs`：

- `ENABLE_FILE = "enabled.txt"`（`:22`）已经存在，安装时由 `arrange_for_ue4ss`（`:365-371`）写入空文件，**从没被读取或删除过**
- 新增 `set_enabled(dir_name: &str, enabled: bool)`：
  - 只处理 `ue4ss-mods.json` 注册表里登记过的目录（`ue4ss_mods.rs:44-46`）
  - `enabled = true` → 写一个 0 字节 `enabled.txt`（已存在则跳过）
  - `enabled = false` → 删 `enabled.txt`（不存在则视为已停用）
  - 目录不存在 → 报「这个 mod 的目录不在了」，不静默成功

### 1.3 三个收窄点（已核实的插入位置）

| 位置 | 文件:行 | 现在的行为 | 要加的 |
|---|---|---|---|
| 进合并包 | `mods.rs:308-319` `mods_to_install` | 只收 `kind=="pak"` 且文件在盘 | `&& !r.disabled` |
| 冲突检测 | `mods.rs:1027-1039` `scan_conflicts` | 全部记录，按 `installed_at` 排 | 过滤 `disabled`；排序改按 `name` |
| 安装前预检 | `mods.rs:961-998` `precheck_install` | 全部记录当已装 | 过滤 `disabled` |

> **注意**：`mod_lints::ConflictingModsLint` 是**死代码**（`run_lints` 全仓无调用方），别去改它，改错了也没人发现。

### 1.4 M0 核对结论（2026-11-17 只读核对，未改代码）

1. **记账结构**：`InstalledRecord` 在 `app/src-tauri/src/ipc/mods.rs:58-84`，正好 12 个字段（id / name / file_id / filename / size / path / source / original_path / content_hash / missing / installed_at / kind）。`disabled` 必须写 `#[serde(default)]`，否则现有的 12 字段 JSON 会反序列化失败。前端 DTO `InstalledMod` 在 `mods.rs:27-42` 与 `app/src/api.ts:153-167`，两边同步加。
   快照已在 `app/src-tauri/src/snapshot.rs:158-163` 把 `records_dir_at(data_root)` 整目录复制成 `installed/`，回滚在 `:294-298` 反向复制回来——新字段自动跟着快照走，**确实不用额外处理**。

2. **合并顺序 vs 冲突顺序（决策 11 成立）**：`load_records` 末尾 `mods.rs:162` 按 `name` 排序，`mods_to_install`（`:308`）保持顺序，`game::apply`（`app/src-tauri/src/game.rs:152`）按切片顺序合并 → **合并顺序 = 名字序**。`scan_conflicts`（`:1028`）先 `records.sort_by_key(|r| r.installed_at.unwrap_or(0))`（`:1030`）→ **冲突顺序 = 安装时间序**，两者不一致。
   额外发现：`scan_conflicts` 上方注释（`:1021-1024`）写「跟后端真正合并时的顺序一致，所以结果能当真」——这句是错的，M1 改排序时**必须一并改掉注释**，否则后面的人会照着错的注释再改回去。

3. **三个收窄点位置核实**：
   - 进合并包 `mods_to_install`（`:308-320`）：先 `filter(|r| r.kind == "pak")` 再 `filter(|m| m.path.exists())`；`&& !r.disabled` 加在第一个 filter 里。
   - 冲突检测 `scan_conflicts`（`:1028-1040`）：全量记录 → 按 `installed_at` 排序 → 交给 `manifest::scan`；改成先 `retain(|r| !r.disabled)` 再按 `name` 排。
   - 安装前预检 `precheck_install`（`:962-999`）：`records.iter().map(Incoming)` 把**全部**记录当已装；改成只取 `!disabled` 的。
   - 补充①：`rebuild_from`（`:362-378`）空列表走 `game::clear()`，而 `clear` 会删 `mods_P.pak`（`game.rs:253-257`）并把加载器 DLL 换回原版（`:259-268`）→「全部停用 = 回到原版」成立，决策 4 可落地。
   - 补充②：`blocked_by_running_game()`（`:391`）返回 `Option<(code, message)>`，新命令照现有写法 `if let Some((code, message)) = blocked_by_running_game() { return ApiResult::err(code, message); }`。

4. **`enabled.txt`**：常量在 `app/src-tauri/src/ue4ss_mods.rs:22`；`arrange_for_ue4ss`（`:357-375`）在 `has_dll || has_lua` 且文件不存在时写 0 字节（`:368-370`）。全仓只有这一处写，**没有任何地方读取或删除**（`ue4ss_health.rs` 读的是 `UE4SS.log` 文本，不是这个文件）。脚本 mod 落地目录 = `Win64\Mods\<dir>`（`mods_dir`，`:179`），注册表 = `<数据目录>/ue4ss-mods.json`（`registry_file`，`:44`），条目 `ScriptMod { id, name, dir, installed_at }`（`:29-38`）。
   §1.2 引用的 `ue4ss_mods.rs:365-371` 实际是 `:357-375`（函数体），写入点在 `:368-370`。

5. **脚本 mod 夹具与计划不符（M4 需要处置）**：本机当前**没有可用的脚本 mod 夹具**——
   - `D:\steam\steamapps\common\Deep Rock Galactic\FSD\Binaries\Win64\Mods` 不存在；
   - 全盘只有一个登记表 `_tools/_m74-data/ue4ss-mods.json`，内容是 `{"mods":[]}`；
   - `_tools/fixtures/` 只有 `small-mod.zip`、`other-mod.zip` 两个 **pak** 包，没有 `main.lua` / `main.dll` / `main.js` 的脚本包。
   
   M2 单测本来就不碰真实目录（计划已要求用临时目录构造），不受影响。受影响的只有 M4 的第 4 条（停用脚本 mod → `enabled.txt` 消失）：需要现场造一个夹具——临时目录里放 `main.lua`，用 `import_local` 导入成脚本 mod，测完删掉；或者把 M4 第 4 条降级为单测覆盖。**按前一种做，不额外占用游戏目录之外的任何东西。**

6. **死代码确认**：`mod_lints::ConflictingModsLint` 只在 `app/src-tauri/src/mod_lints/mod.rs:329` 被 `run_lints` 内部使用，而 `run_lints`（`:318`）全仓没有调用方 → 确实是死代码，改它不会有任何报错，也不会有效果。

## §3 验收（可演示）

1. 停用一个 pak mod：列表立刻灰显并标「已停用」，进游戏它不生效
2. 全部停用：`mods_P.pak` 消失，游戏回到原版状态
3. 启用回来：合并包重建，mod 又生效
4. 停用一个脚本 mod：`ue4ss\Mods\<名字>\enabled.txt` 消失，行内提示「重启游戏后生效」
5. 冲突检测里不再出现已停用的 mod
6. 顶部写「已装 N（其中 M 停用）」，今天页写「有 N 个新版本（其中 M 个已停用）」

## §4 明确不做

- 「全部停用 / 全部启用」按钮（决策 13）
- 把脚本 mod 目录挪到 `Mods.disabled\`（决策 6）
- 停用/启用时生成快照（决策 7）
- 「待应用」中间态（决策 8）
- 停用状态的批量迁移工具（老记录自动按 `false` 读，不需要迁移）

## §5 风险与已知变动

1. **合并顺序与冲突顺序不一致是既有 bug，本版修**——修完之后，冲突报告里「谁覆盖谁」的结果可能与之前不同。这不是新 bug，是以前报错了。**必须写进 CHANGELOG 的「变更」而不是「新增」**。
2. **全停用会删 `mods_P.pak`**——以前只有「一个 mod 都没有」才删。同样写进「变更」。
3. 脚本 mod 的 `enabled.txt` 用户可能手动动过：**以实际文件状态为准**，不假设「我们装的它一定存在」。
4. `blocked_by_running_game` 必须覆盖新命令——停用脚本 mod 时游戏正在运行，删文件会失败或留下半状态。

## §6 红线

- 只碰 `ue4ss-mods.json` 登记过的目录；MintCat 装的、用户手放的一律不碰
- 停用**不删任何 mod 文件**（唯一的删除是脚本 mod 的 `enabled.txt` 这个 0 字节标记）
- 既有命令签名一个不改，只新增 `set_mod_enabled`
- 界面不许出现「合并包」「GVAS」「pak」这类词
